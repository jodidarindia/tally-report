# FLOWRA Tally Sync Agent v9.8.35 — Krishna Sales Corp resolution notes
**Release date:** 29 Sep 2026
**Predecessor:** v9.8.34 (guid-preflight-only, still logged 30 s timeouts on sales exports)
**Symptom:** repeating `Tally request timed out (30s)` starting at Phase 2 (Sales Vouchers). Not a GUID issue.

## Diagnosis
Reading the customer's log carefully:

```
20:02:12 - Got 4244 stock items                        ← GUID/preflight path is FINE
20:02:14 - Voucher types: 34 display names across 24 parents
20:02:14 - Requesting sales: 01-Apr-2025 to 30-Apr-2025 ← Sales General
20:02:44 - Tally request timed out (30s)                ← +30 s
20:03:14 - Tally request timed out (30s)                ← Sales Net Special Rate
20:03:44 - Tally request timed out (30s)                ← SALES Pidilite Raipur
20:03:44 - Requesting sales: 01-May-2025 to 31-May-2025 ← moves on, same story
20:04:14 - Tally request timed out (30s)
```

Every heavy voucher-type × month request is hitting the 30 s wall. Krishna's ledger has 4244 stock items and 3 sales voucher types — an EXPLODEFLAG=Yes month export legitimately takes 60-120 s on Tally Prime 7.0 with this data size. **Tally is NOT crashing** — it's still responsive to ping, still serving small collections. It just can't finish a monthly voucher export in 30 s.

## Fix (v9.8.35)

### 1. Separate `EXPORT_TIMEOUT` for heavy calls
- New module-level constant `EXPORT_TIMEOUT = int(os.getenv('EXPORT_TIMEOUT', '180'))` — 180 s default, overridable via env var.
- `_post()` and `_do_post()` gained a `timeout_override` param. Lightweight Collection / Function requests still use the 30 s `REQUEST_TIMEOUT` (fail fast on connection issues); heavy Export Data calls pass `timeout_override=EXPORT_TIMEOUT`.
- Applied to all heavy voucher-month fetches: sales, receipts, credit_notes, journals, stock_journals, purchases, debit_notes, contra, plus per-FY balance-sheet.

### 2. Adaptive window narrowing (`_export_voucher_window`)
- New helper method wraps every sales-voucher export.
- On timeout, splits the window in half and retries the two halves.
- Recurses up to 6 levels (month → 15 days → 7 → 3 → 2 → 1 day) so a single stubborn slice never stalls a whole month.
- Result-collector (`_collect_vouchers_from_result`) flattens the recursion transparently — call sites don't change.

### 3. Better timeout diagnostics
- Timeout log message now names the debug slug of the failing request, e.g.:
  ```
  Tally request timed out (180s) — sales_sales_general_20250401_20250430
  ```
  Support can now pinpoint the offending voucher-type + date-window without digging into raw XML dumps.

## Zero-impact for small tenants
Small ledgers still get answers in ≤5 s from Tally, well under the 30 s default — they never touch the 180 s ceiling and never trigger adaptive splitting. Only large tenants (Krishna) benefit from the new headroom.

## If it's STILL slow
- Env override: set `EXPORT_TIMEOUT=300` in a `.env` file next to the .exe to bump to 5 minutes.
- Confirm the Tally PC isn't running a full backup / verification concurrently — Tally goes single-threaded during those operations.
- Check `Krishna_Sales_Corporation_(from_1-Apr-25)\sales_*_raw.xml` in `%LOCALAPPDATA%\Flowra\export_cache` — if a monthly XML file is 50+ MB, that's a signal to raise splitting depth to 8.
