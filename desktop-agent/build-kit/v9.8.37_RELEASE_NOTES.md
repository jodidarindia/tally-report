# v9.8.37 — AlterID-Gated Full Sync

**Release date:** 2 Oct 2026
**Previous:** v9.8.36 (rollback to v9.8.31 fetch behaviour)

## What changed

Full-sync (previously every 20 min, now every 60 min) now honours Tally's
`$$LastAlterIdMaster + $$LastAlterIdVouchers` counter the same way the
5-min quick-sync has done since v9.8.23.

**If nothing changed in Tally since the last successful full sync →
the ENTIRE sync is skipped (not just vouchers).** The AlterID counter
covers masters (stock items, ledgers, groups, customers, creditors) AND
vouchers, so this is safe.

## Why

Krishna Sales Corp reported "41 minutes still syncing FY 25-26" on
v9.8.36. Diagnosis of their log: the sync wasn't stuck — the 17-min
full sync had already completed, but the 20-min scheduler re-triggered
a SECOND full sync while the user was watching. The agent was correctly
synced but kept re-fetching the same 20k+ vouchers every 20 min even
when Tally hadn't changed.

Before: full sync re-fetched ~20k vouchers + ~2500 ledgers every 20 min.
After: full sync skips Tally entirely when `$$LastAlterId` is unchanged,
taking ~2 seconds instead of ~17 minutes on idle periods.

## Safety guards

1. **First-ever full sync** still runs (no baseline → no gate).
2. **User-triggered Resync** still runs — the resync command handler
   now also drops the `alter_id_full::<company>` baseline from
   `sync_state.json` so the gate can't short-circuit it.
3. **AlterID detection failure** falls through to a normal full sync
   (never silently skips).
4. **Partial sync (any failed phase)** does NOT save the AlterID
   baseline, so the next cycle re-attempts the failed phase.

## Impact

| Scenario | v9.8.36 | v9.8.37 |
|---|---|---|
| First sync | 17 min | 17 min |
| Nothing changed in Tally | 17 min every 20 min | ~2 sec every 60 min |
| A few new vouchers | 17 min | 17 min (full sync, honours quick-sync delta inside the hour) |
| User clicks Resync | 17 min | 17 min |
| Scheduler frequency | every 20 min | every 60 min (quick 5-min still runs) |

Expected daily Tally load on Krishna Sales Corp: dropped from
~72 full-syncs/day to ~24 scheduled checks/day, of which most will
be instant AlterID short-circuits.

## What was NOT changed

- Voucher fetch logic in `fetch_sales_month` / `fetch_receipts_month`
  stays byte-identical to v9.8.36 (single request per voucher-type per
  month, 30s timeout, continue on empty — NO recursive window-splitting).
- Quick-sync (5-min) AlterID gate is untouched.
- Multi-company safety preflight is unchanged.
- `access_parser` crash patch in Busy agent is unchanged (different
  codebase).
