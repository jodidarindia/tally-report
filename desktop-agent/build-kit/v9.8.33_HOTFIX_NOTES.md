# FLOWRA Tally Sync Agent v9.8.33 — HOTFIX Build Notes
**Release date:** 27 Sep 2026
**Predecessor:** v9.8.32 (guid-bound, CRASHED on multi-company Tally)
**Severity:** CRITICAL — all v9.8.32 installs must upgrade

## Symptom (as reported)
> "Tally program hanged and crashed with the new agent."

Occurred on Krishna Sales Corporation's shop-floor PC where 3+ Tally companies were loaded concurrently on port 9000.

## Root cause
The v9.8.32 `TallyCollectionClient.fetch_company_guid()` used two patterns known to destabilise Tally when several books are loaded:

1. **`ISINITIALIZE="Yes"`** on a `<COLLECTION>` of `<TYPE>Company</TYPE>` — forces Tally to REBUILD the company cache on every request.
2. **`<SVCURRENTCOMPANY>...`** static variable inside the same Collection request — triggers a company-activation attempt on the requested company.

Combined with a quick-sync tick that fires every few seconds, Tally spent all its time re-building caches and eventually the tally.exe process either hung or crashed with an access-violation.

## Fix
The lookup is now **identical in shape** to v9.8.31's proven-safe `list_of_companies` XML, which has been running for weeks on customer machines without incident:

```xml
<ENVELOPE>
 <HEADER>...<TYPE>Collection</TYPE><ID>FlowraGuidLookup</ID></HEADER>
 <BODY><DESC>
  <STATICVARIABLES><SVEXPORTFORMAT>$$SysName:XML</SVEXPORTFORMAT></STATICVARIABLES>
  <TDL><TDLMESSAGE>
   <COLLECTION NAME="FlowraGuidLookup" ISMODIFY="No">
    <TYPE>Company</TYPE>
    <FETCH>NAME</FETCH>
    <FETCH>GUID</FETCH>
   </COLLECTION>
  </TDLMESSAGE></TDL>
 </DESC></BODY>
</ENVELOPE>
```

- **`ISMODIFY="No"`** replaces `ISINITIALIZE="Yes"` → Tally serves from its existing cache, no rebuild.
- **No `SVCURRENTCOMPANY`** → Tally returns ALL loaded companies; the agent filters by name client-side (case-insensitive).
- **Fetches only `NAME` + `GUID`** → the two `COMPANYGUID` and `BASICCOMPANYFORMALNAME` field names that caused older Tally builds to error out are gone.

## Belt-and-braces additions
- **`_guid_cache`** on `TallyCollectionClient` — a per-process dict of `{name_lower: guid}`. First call populates entries for every loaded company; subsequent calls (even across different sync-cycles / different companies) never hit Tally again. If GUID isn't exposed at all, an empty string is cached for the miss so we don't retry.
- **`_binding_posted`** on `TallySyncAgent` — a per-process set of `{name|guid}` keys. `_ensure_tally_binding()` short-circuits if the same key has already been posted to `/api/agent/tally-binding/bind` this session. The GUID still travels with every sync payload, so the backend's TOFU logic remains authoritative.
- **Backend validator softened** — when a binding exists but the incoming payload has no GUID, the sync is now soft-accepted with a warning log instead of a 400. Older Tally builds that never expose GUID, network hiccups, and first-cycle cache warm-ups no longer strand the customer. **Hard block still fires on GUID MISMATCH** — the only case that can actually corrupt data.
