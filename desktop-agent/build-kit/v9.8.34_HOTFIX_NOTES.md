# FLOWRA Tally Sync Agent v9.8.34 — Second-level HOTFIX Notes
**Release date:** 28 Sep 2026
**Predecessor:** v9.8.33 (STILL crashed Tally on Krishna Sales Corp's PC)
**Severity:** CRITICAL — same customer, single company loaded, still crashing after the first hotfix

## Symptom (as reported after installing v9.8.33)
> "still crashing tally" — only ONE Tally company loaded on the PC.

Since the multi-company complexity was ruled out (single company), the trigger MUST be the GUID XML itself — the customer's Tally build simply cannot serve a Company Collection with a `<FETCH>GUID</FETCH>` on its own.

## New model (v9.8.34)
Two structural changes, plus a nuclear kill-switch.

### 1. Piggy-back the GUID fetch on `list_of_companies`
The v9.8.31 `list_of_companies` XML has been serving the customer without incident for weeks. v9.8.34 adds ONE extra field-fetch line to it:

```xml
<COLLECTION NAME="ListOfCompaniesLoaded" ISMODIFY="No">
    <TYPE>Company</TYPE>
    <FETCH>NAME</FETCH>
    <FETCH>GUID</FETCH>         <!-- ONLY new line vs v9.8.31 -->
</COLLECTION>
```

No new XML request is added anywhere in the codebase. The dedicated `FlowraGuidLookup` collection from v9.8.32/33 is DELETED. GUIDs found in the response are cached on `TallyCollectionClient._guid_cache`.

### 2. `fetch_company_guid()` is now pure dict lookup
The sync loops (both quick-sync and full-sync) still call `self.tally.fetch_company_guid(company)` — but the method no longer issues ANY XML. It returns whatever the preflight already cached, or an empty string. Zero Tally traffic from the hot sync-loop path.

### 3. `disable_guid_lookup` — per-tenant kill-switch
If even the added `<FETCH>GUID</FETCH>` line makes a customer's Tally unhappy (which turns out to be Krishna Sales Corp's exact case), support can toggle a flag WITHOUT any .exe rebuild:

* Via the new super-admin route:
  ```
  PUT /api/super-admin/admins/{username}/toggle-guid-lookup
  ```
  Response: `{"disable_guid_lookup": true, "note": "…picks up on next /auth/me refresh"}`
* Or directly in Mongo:
  ```js
  db.users.updateOne(
    {username:"<krishna-admin>", role:"admin"},
    {$set:{tally_disable_guid_lookup:true}}
  )
  ```

The next agent `/api/auth/me` refresh (every few minutes) pulls the flag → `TallySyncAgent.disable_guid_lookup = true` → `TallyCollectionClient.disable_guid_fetch = true` → the `<FETCH>GUID</FETCH>` line is OMITTED from `list_of_companies` on every subsequent call. Effectively rolls the customer back to v9.8.31 behaviour without any downgrade.

## Post-mortem — why v9.8.33 didn't help
v9.8.33's `fetch_company_guid` used the same *shape* as `list_of_companies` (safe on this PC), but it was still a **separate additional HTTP → XML round-trip to Tally on the first quick-sync cycle**. On the customer's Tally build (details TBD from their logs), the *second* Collection request against `TYPE>Company` while the first was still cached apparently corrupts state — which we now avoid entirely by folding the GUID fetch INTO the existing request.
