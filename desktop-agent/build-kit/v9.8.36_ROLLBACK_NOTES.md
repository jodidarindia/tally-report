# FLOWRA Tally Sync Agent v9.8.36 — Doom-Loop Rollback Notes
**Release date:** 2 Oct 2026
**Predecessor:** v9.8.35 (export-timeout + adaptive splitter — HUNG Krishna Sales Corp)
**Severity:** CRITICAL

## Symptom reported
> *"Still error persists, tally crashed, phase 1 started with april 2025 but may 2025 did not start. check and resolve. In all earlier version till 9.8.31 there was no error of this type."*

User's log cut off at `Stock Journal` voucher-type (10:58:56.373) right after April 2025 sales request. Zero response from Tally for the entire log window. No May 2025 attempt.

## Diagnosis — my v9.8.35 code caused the loop

v9.8.35 shipped two "improvements" that interact badly on a 4244-item ledger:
1. `EXPORT_TIMEOUT = 180s` default for voucher Export Data calls.
2. `_export_voucher_window()` that recursively splits on timeout: month → halves → … → 1-day (6 levels).

For a monthly sales request that genuinely takes 3+ minutes:
- April 2025 Sales General → 180s timeout
- Split: 1-15 Apr + 16-30 Apr → each 180s timeout
- Split again: 4 chunks × 180s
- …down to 30 single-day requests × 180s
- **= ~90 minutes just for Sales General April 2025**
- Same for Sales Net Special Rate, SALES Pidilite Raipur
- → agent spent HOURS on April, user killed the process assuming Tally had crashed

**Honest root cause:** my "fix" was worse than the problem. v9.8.31 would have hit a 30s timeout, returned empty, and moved on to May. Users thought it was working (though technically losing some data on slow months). v9.8.35's "robust" splitter turned that quick move-on into an unending retry.

## Fix (v9.8.36) — restore v9.8.31 semantics

```python
# BEFORE (v9.8.35) — doom-loop
EXPORT_TIMEOUT = int(os.getenv('EXPORT_TIMEOUT', '180'))  # default 180 s!
data = self._export_voucher_window(vt, from_dt, to_dt, slug)
# recursively splits on timeout → up to 90 min

# AFTER (v9.8.36) — identical to v9.8.31
EXPORT_TIMEOUT = int(os.getenv('EXPORT_TIMEOUT', '0'))    # opt-in only
_to = EXPORT_TIMEOUT if EXPORT_TIMEOUT > REQUEST_TIMEOUT else None
data = self._post(xml, debug_name=…, timeout_override=_to)
if not data:
    continue  # move on, exactly like v9.8.31
```

- **`EXPORT_TIMEOUT` default now `0`** → the `_to` resolution falls back to `REQUEST_TIMEOUT` (30s), **byte-identical to v9.8.31**.
- **Adaptive splitter is still on the class** but no longer called from any fetch path. Easy to re-enable in a future release if we ship it with a flag the admin controls.
- All 8 heavy fetches (`fetch_*_month`, `balance_sheet`) updated to the same conditional: `timeout_override=(EXPORT_TIMEOUT if EXPORT_TIMEOUT > REQUEST_TIMEOUT else None)`. Opt-in only.

## Preserved from v9.8.32-9.8.35
- GUID binding (TOFU) + hard-block on mismatch.
- `disable_guid_lookup` kill-switch (super-admin + Mongo).
- `fetch_company_guid()` cache-only reads (zero XML cost in sync loops).
- Better timeout log messages (now showing the exact debug slug).
- `_post` / `_do_post` gained `timeout_override` param (kept for future opt-in).

## For admins with heavy ledgers who STILL want the longer wait
Drop a `.env` next to `FlowraTallyAgent.exe` with:
```
EXPORT_TIMEOUT=180
```
This re-enables the 180s wait for Export Data calls **without** the recursive splitting. If a month still times out, the agent returns empty and moves on — never doom-loops.

## Lessons learned
- "Robust" is not always better. v9.8.31's "fail fast, move on" was the right behaviour for an incremental sync — the next cycle (20 min later) retries anyway.
- Adaptive splitting is useful ONLY when a single request has a real chance of succeeding; when the whole month genuinely needs > N seconds, splitting into days multiplies the pain.
- Any future "defensive" code added to a hot path must come with a kill-switch flag flagged on by default.
